# Scribe Help Files Update

## Current Status

The help files in 'scribe/trunk_os/help' are probably quite out of date and I'd like to scan through them and sync them up to what actually happens in the code. I'm not sure what the best way to do this is.

One thing I do know is that you will need to understand how the main resource file 'scribe/trunk_os/resources/Scribe.lr8' relates to code in the Scribe email client. It's an XML file that defines various dialogs used and translatable strings, menus and so on.

## How lr8 relates to code (and therefore to help)

- `Scribe.lr8` is the live UI text source: `<String Ref=.. Cid=.. Define=.. en="..." xx="..."/>` entries in
  string-groups, with `Define` names resolved to numbers by the generated `resources/resdefs.h`
  ("Generated by LgiRes"). Code uses those names (`IDM_` menus 95, `IDC_` controls 753, `IDS_` strings 549, `IDD_` dialogs 48).
- Menus are assembled at runtime from lr8, not hardcoded: `ScribeApp.cpp:964` `Menu->Load(this, "ID_MENU", GetUiTags())`.
  Menu items carry platform gates (`Tag="!mac"`, `Tag="!xgate"`), so the menu the help describes is per-platform.
- Consequence: any UI label quoted in the help is only correct while it matches the `en=` value in lr8. That is a
  machine-checkable relationship, which is the useful lever for keeping help in sync.
- Anchors are a code contract, not just HTML: `LaunchHelp("filters.html#cond")` (ScribeFilter.cpp),
  `LaunchHelp("filters.html#bayes")` (BayesDlg.cpp), and the per-tab option anchors built in
  OptionsDlg.cpp:842 and ScribeAccountUI.cpp:279. Renaming an anchor breaks the app, so anchor names are frozen.
- Help is rendered by the in-app browser (`USE_INTERNAL_BROWSER 1`, `ScribeAppMail.cpp:1236` -> `LBrowser` over `Html2::LHtml`
  in `lgi/trunk/src/common/Lgi/Browser.cpp`). `Html2` supports local `iframe` loading through `LDocumentEnv`, so the
  `iframe` navigation frame in `help/index.html` renders in-app. Remote `iframe` loading is not supported for security
  reasons (`Html2.cpp:6508`). The parser parses iframe source text as fallback content only when the iframe has no loaded
  content from `LDocumentEnv::GetContent()`. When loaded iframe content exists, engines that support iframes do not render
  `No iframe support.` as content.

## Still out of sync (evidence)

- The UI index tree is generic, but lr8 menu items carry platform gates (`Tag="!mac"`, `Tag="!xgate"`) and code gates
  (`IDM_POP3ONLY`, `IDM_IMAPONLY`, `IDM_LDAPONLY`), so a per-platform tree is not currently represented in help.
- Menu items with no dedicated help section: Work Offline, Security Settings, Logout, Find, Text/HTML editor, Show

- Toolbar contents are not defined in lr8 (the image list only has `IDT_CALENDAR`, `IDT_CALENDAR_NEW`,
  `IDT_CALENDAR_MONTH`), so the help toolbar list cannot be machine-checked against lr8.
- `calendar.html`, `contacts.html`, `menu.html`, `webdav.html` were touched 2026-11-14; the rest is from 2026-09-08, so the pass is already half started.


## Approach

Automation can find drift; it cannot write prose, so split the work into a mechanical layer plus a human pass.

1. Mechanical layer (link half is already done; formalise it so it stays green):
   - `utils/help-audit.py` (or a unittest in `unittests/`) that builds the inventory from lr8 + code and reports:
      - every `LaunchHelp("page#anchor")` literal and every `href`/`src` target must resolve to a file and a `name=` anchor,
        checking both quote styles and treating `help/scripting/` as the lgi docs and `help/..` as the resource root;
     - every `en=` label from lr8 menus/dialogs that never appears in help text (uncovered UI);
     - every UI label quoted in help that does not exist in lr8 (renamed/removed UI);
     - orphan pages and duplicate sections.
   - Keep the audit as the invariant; help prose edits then cannot regress the links.
2. Human pass, page by page, ordered by how the user actually reaches a page from the app
   (`install.html`, `email.html`, `filters.html`, `calendar.html`, `contacts.html`, `ui.html`, `import.html`, `plugins.html`,
   `scripting.html`, `print.html`, then `features.html`/`intro.html` merged into `index.html`).
   - For each page: read the lr8 string-group + the code that builds that view, and restate the page against what the code
     does now; quote UI labels exactly as `en=` so the audit can match them.
   - Keep anchor names stable, add new ones rather than renaming.
 3. Rendering fixes independent of content: keep `help.css` to the subset the in-app browser supports, and rely on
   `Html2` for local `iframe` navigation instead of replacing the nav `iframe` with inline navigation.
4. Decide what help owns: the site (memecode.com) already duplicates overview content. Keep in-repo help as the single
   source for UI behaviour and let the site hold screenshots/links, otherwise the same drift reappears.

Ordering note: the audit inventory is worth building before any rewriting, because it tells you which pages have real drift
and which are already fine, instead of reading all 15 pages by hand.
